01 · Alcance y entregables

Resumen ejecutivo

El trabajo completa el análisis y la validación técnica de la gestión de pagos mensuales para Autos Colombia. El flujo permite asociar una mensualidad con un usuario y un período, controlar membresías, registrar pagos y consultar estados. Esta funcionalidad permanece separada del cobro de las estancias para preservar el comportamiento existente de entradas y salidas.

Entregables preparados

  • Requerimientos funcionales/no funcionales y reglas del negocio para pagos mensuales.
  • Historias de usuario con criterios de aceptación.
  • Fuentes de diagramas de casos de uso, secuencia y componentes de las tres iteraciones, en PlantUML.
  • Mockup navegable en HTML estático para pagos mensuales.
  • Plan de pruebas resumido y checklist de cierre de Iteración 3.
  • Entrega académica en PDF y este informe integral en PDF.
  • Backend de pagos mensuales, membresías, autenticación/sesiones y control de acceso por roles, con pruebas automatizadas.
Criterio de continuidad: el pago mensual no reutiliza la tabla del pago por estancia. La clave lógica usuario/período evita pagos duplicados; la idempotencia se verifica en el servicio y en solicitudes HTTP concurrentes.

Componentes técnicos

Backend

Java 21, Spring Boot, Spring Data JPA y API REST. Servicios, controladores, repositorios y validaciones gestionan membresías y pagos.

Interfaz y datos

React/Vite consume la API. MySQL almacena usuarios, membresías, pagos mensuales y pagos por estancia con integridad referencial e índices.

02 · Reglas y controles

Reglas de negocio y seguridad

Política económica confirmada

Mes completo: si la membresía está vigente al menos un día del período mensual, se cobra el valor mensual completo ingresado manualmente. No se prorratea ni redondea. La regla aplica a pagos nuevos; los registros históricos se conservan sin cambios.

Se aceptan períodos en formato YYYY-MM actuales o anteriores, no futuros; el valor debe ser positivo y el método debe ser permitido. La fecha y hora oficiales provienen del servidor. Una membresía debe cruzarse con al menos un día del mes para cubrir ese período.

Idempotencia y persistencia

  • Un pago nuevo se crea con respuesta HTTP 201.
  • Una repetición con el mismo usuario, período, valor y método devuelve el registro existente (HTTP 200), sin duplicarlo.
  • Si ya existe el usuario/período con valor o método diferente, se rechaza como conflicto (HTTP 409) y no se sobrescribe el pago.
  • MySQL aplica clave foránea, unicidad usuario/período, restricción CHECK de valor positivo e índice compuesto para consulta.

Autenticación y autorización probadas

ControlResultado comprobado
Sesión y credencialesLogin inválido 401; contraseñas almacenadas con BCrypt.
PermisosAdministrador puede consultar mensualidades; operario recibe 403. El operario puede consultar vehículos (200).
CSRF y logoutEscritura sin token CSRF rechazada (403); logout 204 e invalida la sesión.
Sesión anónimaConsulta mensualidades sin sesión rechazada (401).

Los permisos descritos se verificaron en las rutas indicadas; no se afirma cobertura RBAC granular de todas las operaciones del sistema.

03 · Verificación

Resultados de las pruebas

Pruebas automatizadas

mvn test: 18 pruebas aprobadas, 0 fallos y 0 errores: 8 de servicio, 3 de controlador y 7 de integración HTTP con H2. Se incluye el caso de membresía vigente un día: el valor mensual manual de $125.000 se conserva completo, sin prorrateo.

MySQL 8.4 y API HTTP

  • Esquema creado y aplicación conectada a MySQL 8.4.13 en un entorno efímero.
  • 20 solicitudes concurrentes idénticas: 1 respuesta 201, 19 respuestas 200 y una sola fila/pago.
  • Datos conflictivos rechazados con 409; período futuro y valor cero rechazados con 400.
  • Inserciones directas inválidas rechazadas por CHECK y FK; `EXPLAIN` usa el índice único compuesto de usuario y período.
  • Login, roles, CSRF, logout, sesión invalidada y BCrypt verificados con MySQL.
  • No se particionaron las tablas: el volumen académico no justifica su complejidad adicional.
Alcance de evidencia: las pruebas MySQL se realizaron con un contenedor local desechable y datos sintéticos. No constituyen certificación del entorno productivo. El build de frontend fue validado previamente; no se modificó frontend en esta última actualización.

Fuentes del proyecto

Los requisitos e historias están en docs/requerimientos.md y docs/historias_usuario.md. El plan/checklist están en docs/pruebas/; los diagramas PlantUML en docs/diagramas/; el mockup en docs/mockups/pagos-mensuales.html. El documento académico es docs/entrega_iteracion3.pdf.

04 · Cierre y estado

Conclusiones y pendientes

  • La Iteración 3 tiene una regla económica inequívoca y documentada: mes completo al existir al menos un día de vigencia.
  • Los pagos mensuales se asocian a usuario/período; validaciones, restricciones e idempotencia protegen su integridad.
  • Las pruebas de servicio, HTTP, MySQL e idempotencia concurrente respaldan los resultados reportados.
  • Los diagramas editables se entregan como fuentes PlantUML, y el mockup HTML es una maqueta estática.

Pendientes transparentes

  • El repositorio proporcionado es sofia0823/parqueadero-aut-colom, público, rama v1.0. El proyecto y sus entregables están publicados; se conservó el historial y los archivos remotos no conflictivos, y la rama local sigue el remoto.
  • Configurar HTTPS y SESSION_COOKIE_SECURE=true en despliegue; ejecutar pruebas en el ambiente de producción antes de liberar.
  • El CRUD de usuarios y RF-09 (novedades) siguen fuera de la implementación validada.
  • Las fuentes diagramáticas están en PlantUML, no como archivo nativo de StarUML (.mdj); se indicó que las fuentes son suficientes para esta entrega.
Resultado: documentos, diagramas, mockup y evidencia de pruebas quedan alineados con la regla acordada y los resultados de 18 pruebas automatizadas. La publicación del repositorio y la validación de despliegue permanecen como tareas externas a este cierre.
